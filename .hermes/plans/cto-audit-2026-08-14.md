# CTO Audit — ReClass (eShule) — 2026-08-14

Scope: whole-codebase review with emphasis on the **user journey**, post single-tenant
collapse (commit 8221bbf). Verified against real source + live DB + test gates.

## Executive Summary

The project is in **good health for a single-tenant school SaaS**: TypeScript strict mode is
genuinely on (svelte-check 0/0), the money path (M-Pesa STK → Daraja callback →
`reconcile_payment` RPC) is idempotent and fail-closed under rate limits, and the user journey
is coherent across 6 roles. The biggest *honest* risks are two pieces of **dead multitenant
scaffolding that misleads security reviewers** (RLS policies + a test that asserts cross-tenant
isolation that the app no longer enforces) and a handful of **UX-safety gaps** (double-submit on
some forms, `any`-typed data in templates, an unused `tenants` table). None are data-loss or
shipping blockers today; all are cleanup that compounds if left.

## Verified state (real runs)

- `npm run typecheck` (svelte-check) → 0 errors / 0 warnings
- `npx vitest run` → 135/135 passing

## Detailed Findings

### 🔴 Critical — NONE
No data-loss, no 500-on-load, no broken navigation. The single-tenant collapse did not break
the journey.

### 🟠 High

1. **Dead RLS scaffolding misleads security reviewers** (Security / Honesty)
   - 42 `ENABLE ROW LEVEL SECURITY` + ~60 `CREATE POLICY` across migrations, but **zero** code
     paths call `set_tenant_context` (only `database.types.ts`, a test, and a migration test
     reference it). Every query uses the service-role client (`locals.srv`, 62 usages vs 4 anon).
   - In single-tenant this is *harmless at runtime* but a **trap**: anyone auditing assumes RLS
     protects data. Either (a) delete the RLS migrations + the `tenant_isolation.sql` DB test, or
     (b) leave them but add a top-of-migration comment "RLS disabled by design — service-role SSR".
   - Files: `supabase/migrations/*enable_rls*`, `*tenant_isolation*`, `supabase/tests/tenant_isolation.sql`.

2. **`migrations.test.ts` asserts dead cross-tenant RLS behavior** (Testing / Honesty)
   - `src/routes/__tests__/migrations.test.ts:59-75` ("tenant isolation coverage") asserts a real
     DB cross-tenant *denial* test in `supabase/tests/tenant_isolation.sql`. That behavior is no
     longer enforced by the app (service-role bypass). Same class of issue as the
     `tenant-isolation.test.ts` I already deleted this session.
   - Action: prune the "tenant isolation coverage" describe block + the now-dead DB test, OR
     rewrite it to assert "RLS is present but app uses service-role" so it documents reality.

3. **Form double-submit risk on money-adjacent forms** (UX Safety)
   - `FeeManager.svelte:113`, `admin/settings`, `finance/expenses`, `finance/+page.svelte` use
     `disabled={submitting|saving}` — good. But `parent/pay/+page.svelte:139` STK submit is
     `disabled={!selectedStudentId || !selectedFeeTypeId || loading || polling}` — guards on
     *selection* not on an explicit `submitting` flag during the `functions.invoke('stk')` await.
     A slow Daraja response (2-5s) lets a parent click twice → two STK pushes. Idempotency exists
     downstream (one `checkout_requests` row per invoke), but two pushes to the same phone is a UX
     bug and a rate-limit hit.
   - Action: add `let submitting = $state(false)` and gate the button on it around the invoke.

### 🟡 Medium

4. **`any`-typed data into templates** (Code Quality / Data Integrity)
   - `parent/pay/+page.svelte:15,18,26,27` uses `data.students.find((s: any) => ...)` and
     `data.feeTypes.find((f: any) => ...)`. A renamed DB column (e.g. `fee_type_id` → `feeTypeId`)
     would silently become `undefined` in the UI. The `DataTable` generic accepts `data: any[]`.
   - Action: type `data` via the generated `PageData` / a `Student`/`FeeType` row type from
     `database.types.ts`.

5. **Unused `tenants` table + `tenant_id` columns everywhere** (Dead Code / Clarity)
   - Post single-tenant, `tenants` table has 1 row and every query filters `.eq('tenant_id',
     TENANT_ID)`. Harmless (intentional Option A), but the `tenants` table + `tenant_modules`
     table are now orphaned config. `getEnabledModules` was removed; `tenant_modules` may be
     unreferenced.
   - Action: leave columns (re-tenant-ready), but consider dropping the `tenants`/`tenant_modules`
     tables in a later migration if re-tenanting is permanently off the table.

6. **`notifications` delete uses native `confirm()`** (UX Safety)
   - `notifications/+page.svelte:64` `deleteSelected` and `:146` `deleteOne` call
     `confirm(...)` — works, but inconsistent with the bits-ui `ConfirmDelete` modal used by
     `DataTable.svelte`. Mixed affordances. Low severity; align for consistency.

7. **Catch blocks swallow errors silently** (Observability)
   - `parent/pay/+page.svelte:51` `catch {}` (poll errors — OK to ignore) and
     `rate-limit.ts:55` / `payroll.ts:298` catch and *do* log. The STK try/catch around
     `functions.invoke` should surface `fnErr` to the user (currently only sets generic error).
   - `payroll.ts:298` logs but the call site may not show the user why payroll claim failed.

### 🔵 Low

8. **Lint warning backlog (160, 0 errors)** — mostly `a11y` (missing `for`/`id`, dialog focus,
   `on:click` → `onclick` deprecation). Non-blocking but should be burned down for a11y compliance.
9. **Marketing/brand**: copy says "eShule" consistently; no template contamination found (no
   wrong-currency, wrong-brand, or foreign testimonials). Good.
10. **Dependency bloat**: M-Pesa/Supabase stack is lean; no unused runtime deps detected in the
    server path. `bits-ui` v1 + `tailwindcss` v4 are current.

## Journey map (verified coherent)

routes (verified earlier this session).
